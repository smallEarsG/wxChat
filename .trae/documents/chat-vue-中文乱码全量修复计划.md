# `chat.vue` 中文乱码全量修复计划

## 一、Summary
- 目标：修复 `e:\test2\wxChat2\wxChat\pages\chat\chat.vue` 全文件中文乱码与由乱码引起的语法/模板错误，保持现有业务逻辑不变。
- 成功标准：
  - 页面可见中文文案全部可读，无 `鍏/鎺/涓?/璇?/鈥?` 等乱码。
  - `GetDiagnostics` 对 `chat.vue` 无新增报错。
  - 时间格式、提示文案、菜单文案、Toast 文案可正常显示。
  - 不修改功能行为（仅文本与被乱码破坏的拼接语法修复）。

## 二、Current State Analysis
- 已确认乱码分布广泛，主要在以下区域：
  - 模板层：注释、按钮文案、功能区标题、消息类型注释、拖拽提示文案、通话状态文案。
  - 脚本层：注释、配置项文案、Toast 文案、日志文案、字符串拼接模板（部分被 `?` 破坏）。
  - 样式层：注释文字、部分行内说明。
- 关键风险点（已探测）：
  - 字符串模板被截断或混入乱码占位符（如时间格式函数中的 `month/day` 拼接）。
  - 个别 HTML 标签文本被污染（如历史出现的 `.../text>` 类问题）。
  - 大文件（>128KB）无法整文件读取，需要分块修复。

## 三、Proposed Changes

### 1) 分块扫描并建立修复清单（不改逻辑）
- 文件：`pages/chat/chat.vue`
- 做法：
  - 以 `Read(offset/limit)` + `Grep` 分段扫描。
  - 将乱码分为四类：
    - A 类：用户可见文案（必须修复）
    - B 类：业务字符串（必须修复）
    - C 类：注释乱码（建议修复）
    - D 类：语法受损片段（必须优先修复）
- 目的：降低一次性改动风险，避免误改逻辑。

### 2) 优先修复 D 类（语法受损）与 A/B 类（可见与业务字符串）
- 文件：`pages/chat/chat.vue`
- 修复范围：
  - 模板中可见文字：按钮、标题、提示、菜单项、功能入口。
  - 脚本中的用户提示：`uni.showToast`、状态文案、消息快照文案。
  - 字符串模板拼接：日期/时间/消息预览等被 `?` 破坏的位置。
  - 业务状态字符串：如“已取消”“语音通话”“通话时长”等。
- 原则：
  - 仅改文本与拼接语句，不变更判断分支和数据结构。
  - 语义优先使用现有上下文可推断的标准中文。

### 3) 清理 C 类（注释乱码）并统一术语
- 文件：`pages/chat/chat.vue`
- 做法：
  - 将乱码注释替换为可读中文注释。
  - 统一术语（如“虚拟滚动”“拖拽”“占位符”“消息插入”等）。
- 目的：提高可维护性，避免后续误读。

### 4) 一致性回归检查
- 文件：`pages/chat/chat.vue`
- 检查项：
  - 同一词汇前后一致（如“收款/转账/红包/文件/提示”）。
  - 同一状态文案一致（如“已开启/已关闭”“已取消”）。
  - 组件 class 名称一致（如 `input-box` 与样式定义对应）。

## 四、Assumptions & Decisions
- 决策 1：本次仅修复 `chat.vue`，不扩散到其他文件。
- 决策 2：以“修文本和语法损坏”为边界，不做功能重构。
- 决策 3：注释乱码一并清理，因为用户要求“检查整个文件乱码并修复”。
- 假设：
  - 原意中文可由上下文稳定推断；若个别词义无法确定，采用同文件已存在术语保持一致。
  - 该文件当前业务流程以现状为准，修复后不改变交互路径。

## 五、Verification Steps
- 执行后验证：
  1. `GetDiagnostics(uri=chat.vue)`：确认无新增报错。
  2. `Grep` 复扫乱码特征串（`鍏|鎺|璇|鈥|锟|涓?` 等）：
     - 用户可见文本与业务字符串应清零或仅剩极少注释残留。
  3. 重点代码片段复读：
     - 时间格式函数输出拼接是否正确。
     - 提示/转账/通话相关文案是否恢复正常中文。
     - 模板标签结构是否完整（无坏标签）。
  4. 若有残留乱码，仅做增量补丁直至达标。
